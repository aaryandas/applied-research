## Material ambiguities and recommended resolutions

Do not ask the founder to repeat settled platform/provider/deployment/runtime decisions already in context. Current full-app docs select app-managed auth/backend, OpenRouter, isolated Manim Community 0.21 recipes and local Three.js/R3F, and explicitly forbid arbitrary generated-code execution absent new agreement.

1. **Source corpus retrieval/ingestion strategy**: The video explicitly requires open courses/textbooks plus OpenAlex, but does not select a corpus provider/index or rights-aware ingestion mechanism. Read existing AR-16/17/14 contracts before asking. Recommended default where permissible: curated high-trust source-provider adapters that discover original open resources on demand, preserve access/license metadata, cache only permitted content, and expose unavailable content honestly. A broad crawler or paid indexing service needs a concrete decision. Question if unresolved: “For launch, should course/textbook grounding use selected open-source collections discovered on demand, or a pre-indexed corpus we host? I recommend on-demand selected collections first so quality/provenance can be checked without a new corpus service.”
2. **Practical execution boundary**: The founder wants real implementations and publishable artifacts, but does not authorize executing arbitrary generated programs inside Electron or automatically uploading. Existing embedded-tools/external fallback remains the recommendation. Ask only if the founder now wants the app itself to host/run arbitrary projects; otherwise build complete guided handoff/result-return within accepted boundary.
3. **Theses mention vs deferred Playbook**: At 08:31 founder mentions branching “insights and theses.” Current product requires insights supported by ≥2 notes/questions and defers Playbook; no specific thesis interaction is described here. Recommended: retain existing thesis records/links where present, implement approved graph objects first, and clarify whether a new editable thesis object is demanded before changing model/Playbook sequencing.
4. **Open-ended diagnostic policy**: Explicitly selected, but exact number, skip policy, grading/display and evidence-retention fields are unspecified. Recommend short adaptive sequence (background/goal + one concrete diagnostic, follow-up only if needed), allow “not sure,” no unearned numeric mastery label. This is likely design delegation, not a blocker requiring reapproval, unless current contracts contradict it.
5. **Profile scope**: Explicitly useful learning profile, not just Settings; exact fields unspecified. Recommend editable background/goals, topic interests and transparent diagnosis/evidence history; avoid collecting unrelated employment details. Existing design delegation can likely resolve this without user interruption.
6. **Today / production completion conditions**: Video says live wired to production and user says completion today, but neither supplies hosting credentials, purchased rendering or signing/distribution authorization. The project already separates local verification, deployment and spend. Root should inventory concrete existing deployment/live validation access early, report missing access rather than quietly fake results, and carry out all independent work.
