# Scientific paper → structured, sentence-anchored document (state of the art, 2026-09-05)

Scope: parsing and structure extraction only. Reader rendering (F4) and text anchoring (F3) in `presearch.md` are taken as settled. The 6-day deadline and 2 GB server that drove the F2 pick no longer apply.

## (a) Problem statement

Given an arXiv id, a DOI, or an uploaded PDF, produce one block model: ordered, typed blocks (heading with level, paragraph, list, figure + caption, table, display equation as LaTeX → MathML, footnote, reference entry) with inline math and in-text citation markers linked to reference entries, correct reading order across two columns, running headers/footers removed, line-break hyphenation repaired, and a single canonical text with stable document-level character offsets so every sentence has an id that AI citations and human annotations can target. The document is reflowed into the product's typography, never overlaid on the PDF, so math must become selectable text (MathML), not a picture. No shipped parser emits that model directly; the question is which parsers get closest, what they cost, and how to combine them.

## (b) Parser comparison

Benchmarks: **olmOCR-bench** (Ai2; 1,403 PDFs, 7,010 unit tests; English, arXiv-heavy; categories ArXiv / Old-scans-math / Tables / Old-scans / Headers-footers / Multi-column / Long-tiny-text / Base) and **OmniDocBench v1.6** (opendatalab; 1,651 pages, Chinese+English, 10 doc types; overall = mean of text, table TEDS, formula CDM; separate reading-order edit distance, lower is better). Numbers marked *(self)* are vendor-reported; others are from the benchmark owner's table or a third party's run, as cited. Datalab's own analysis says 3–4% of olmOCR-bench tests have wrong or opinionated ground truth and the practical ceiling is ~96–97, so differences of a point or two are noise ([Datalab, "Saturating the olmOCR benchmark"](https://www.datalab.to/blog/saturating-the-olmocr-benchmark)).

## (c) What shipped products do

Only two products expose a full engineering trail (Semantic Reader and Zotero); the rest are inferred from docs, forum posts, or founder statements and are marked accordingly.

- **Semantic Reader / Semantic Scholar** — Parsing: PaperMage in production ("used in the production PDF processing pipeline … for both the literature graph and the paper-reading interface", [PaperMage EMNLP 2023](https://aclanthology.org/2023.emnlp-demo.45.pdf)); pipeline = pdfplumber/pdfalto text, LayoutParser regions, I-VILA token tagging ([Open Data Platform](https://arxiv.org/pdf/2301.10140)); GROBID/ScienceParse were the older path ([S2ORC](https://ar5iv.labs.arxiv.org/html/1911.02782)). Reader: **PDF overlay**, PaperCraft on react-pdf/pdf.js with page image + transparent text layer + overlay layer ([PaperCraft](https://openreader.semanticscholar.org/PaperCraft), [pdf-component-library](https://github.com/allenai/pdf-component-library)). Anchoring: bounding boxes positioned by `computeBoundingBoxStyle` ([BoundingBox.tsx](https://github.com/allenai/pdf-component-library/blob/main/ui/library/src/components/BoundingBox.tsx)); citation cards and formula tooltips are box overlays, math is the PDF's own rendering. Their reflow track (SciA11y) admits "difficulty parsing math equations" ([CACM paper](https://arxiv.org/abs/2303.14334)).
- **alphaXiv** — Reader: the original arXiv PDF. Founder: the first site "only supported HTML (because it was easier to build an annotator for an HTML page). the issue is that a good ~25% of these papers don't render properly" ([HN](https://news.ycombinator.com/item?id=41478690)). Parser and anchoring format: unverified.
- **Elicit** — Anchoring by **text quote** ("cites every claim with exact quotes", [Reports post](https://elicit.com/blog/introducing-elicit-reports/)); PDF viewer for uploads since 2025-01-31 ([changelog](https://support.elicit.com/en/articles/1475137)); the widely repeated "GROBID" claim traces to a libguide, not Elicit — unverified.
- **SciSpace / Typeset** — "We use various parsing tools like Grobid, PyMuPDF and Science-Parse" then chunk + embed ([AAAI 2024](https://ojs.aaai.org/index.php/AAAI/article/view/30578/32740)); reader is the PDF with a "snip tool" for math regions (image, not text) ([help](https://scispace.com/help/en/articles/10750976-how-to-highlight-text-in-chat-with-pdf)); citation mechanism unverified.
- **Paperpile** — pdf.js viewer (console logs show "PDF.js: 1.4.323", [forum](https://forum.paperpile.com/t/highlight-and-annotate-pdfs-in-paperpile/1073?page=2)); annotations written as standard PDF annotations into the file ([forum](https://forum.paperpile.com/t/highlight-and-annotate-pdfs-in-paperpile/1073)). Overlay; no parsing pipeline documented.
- **ReadCube / Papers** — "Enhanced PDF" overlay with tap-able inline citations resolved to the reference list ([ePDF help](https://about.readcube.com/help-center/readcube-enhanced-pdf-reader-epdf/), [inline citations](https://about.readcube.com/help-center/how-can-i-navigate-directly-from-an-inline-citation-to-an-article-reference-2/)); engine and anchor format unverified.
- **Scholarcy** — In-house line classifier ("classify each line … according to its structural and semantic function", [founder post](https://www.scholarcy.com/blog/the-founder-of-scholarcy-phil-gooch)); API returns `structured_content, references, figure_captions, highlights` ([API](https://scholarcy.github.io/slate/)). Reflowed summary cards; anchors are extractive sentences; math handling unverified.
- **Undermind** — only first-party fact: `read_pdfs` "reads full-text PDFs … including from figures, tables, and equations" ([MCP page](https://www.undermind.ai/mcp)); no reader, parser unverified.
- **Consensus** — full text from Semantic Scholar, OpenAlex, own crawl and publisher deals (Sage full text "only to measure search relevance, and generate short, cited previews") ([Library Primer](https://consensus.app/home/blog/consensus-library-primer/), [Sage](https://consensus.app/home/blog/sage-partners-with-consensus-to-bring/)); citations are paper-level with a "full text used" checkmark ([changelog](https://help.consensus.app/en/articles/11954907-consensus-product-changelog)); parser unverified.
- **Explainpaper** — marketing only; served bundles contain no `pdfjs-dist`, `react-pdf`, `mupdf`, `katex` or `mathjax` strings pre-auth; everything unverified ([site](https://www.explainpaper.com/)).
- **Zotero reader** — pdf.js fork as git submodule; **PDF overlay**; `PDFPosition = { pageIndex, rects[][], nextPageRects? }` in PDF user space; reflowed EPUB/snapshot views use W3C selectors (`FragmentSelector` epubcfi, `CssSelector` refined by `TextPositionSelector`); reflowed math via MathJax `mjx-container[data-tex]` ([types.ts](https://github.com/zotero/reader/blob/master/src/common/types.ts), [selector.ts](https://github.com/zotero/reader/blob/master/src/dom/common/lib/selector.ts), [math.ts](https://github.com/zotero/reader/blob/master/src/dom/common/lib/math.ts)).
- **Sioyek** — MuPDF; highlights stored in SQLite as begin/end character positions in "absolute document space" (pages stacked vertically) and re-derived from MuPDF char boxes on load ([database.cpp](https://github.com/ahrm/sioyek/blob/development/pdf_viewer/database.cpp), [PR #742](https://github.com/ahrm/sioyek/pull/742)).
- **arXiv HTML / ar5iv** — LaTeXML; launched 2023-12-18; ~97% of submissions get HTML, ~75% error-free, pipeline updated roughly quarterly, LaTeXML 0.9 due summer 2026 ([2605.16562](https://arxiv.org/html/2605.16562v1), [arXiv blog](https://blog.arxiv.org/2023/12/21/accessibility-update-arxiv-now-offers-papers-in-html-format/)); MathML Core with TeX annotation, `ltx_cite` anchors, stable hierarchical ids. ar5iv holds the back catalogue (sources to end of July 2026, single version per article, batch re-conversion "takes several weeks") ([ar5iv](https://ar5iv.labs.arxiv.org/), [launch post](https://blog.arxiv.org/2022/02/21/arxiv-articles-as-responsive-web-pages/)).

**Takeaway.** Every shipped *reader* in this list overlays the original PDF; the only reflowed, math-as-text rendering of papers in production is arXiv's own HTML. Reflow products (Scholarcy, Elicit) anchor by text quote, which is what F3 already chose.

| olmOCR-bench Headers & footers (↑) | PaddleOCR-VL 97.0 · MinerU 96.6 · olmOCR 2 96.1 · Marker 2 95.9 · Mistral v1 93.6 · Chandra 2 91.4 |

The pattern: end-to-end VLM parsers (MinerU2.5-Pro, PaddleOCR-VL, GLM-OCR, Chandra) order columns better than pipeline heuristics (Marker, Docling), and the two benchmarks disagree on which VLM (MinerU-family wins on the Chinese/English mix, Chandra/olmOCR on the arXiv-heavy set). Docling's ordering is explicitly rule-based (rtree over layout boxes, `reading_order_rb.py`); Marker's is text-layer order plus a 2%-of-page-width column-gap merge rule (`processors/text.py`). Nobody publishes a paragraph-continuation-across-columns metric; Docling (`predict_merges`), Marker (`TextProcessor`), MinerU ("truncated paragraph merging") and Datalab's API (`merge_cross_page`, surcharge) all claim to do it.

**Document-level character offsets.** Only two parsers emit them: Azure DI (every paragraph, table cell, formula, style has `spans[{offset,length}]` into one `content` string, [layout docs](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout)) and PaperMage (`Span(start,end)` into `Document.symbols`, [README](https://github.com/allenai/papermage)). Docling's `charspan` is item-relative — the source sets `charspan=(0, len(text))` and merged continuations `(len(a)+1, …)` — so it is a within-item span, not a document offset. LlamaParse's `grounding.lines[].span` is relative to the item's markdown. Marker, Chandra, MinerU, Mistral, Mathpix, Reducto, GROBID give geometry and/or ids only. Conclusion: F3's decision stands — mint `paperText` and offsets from the block model ourselves; the parser only needs to deliver ordered, typed blocks with hyphenation already repaired. That makes offsets parser-independent, which is exactly what re-parsing with a better model later requires.

Two cheap wins worth noting: (1) Datalab's `add_block_ids` puts `data-block-id` on every HTML block and `extract_links` keeps PDF links ([convert API](https://documentation.datalab.to/api-reference/convert-document.md)); Mistral returns `hyperlinks` per page; Mathpix has `include_hyperlinks`. arXiv PDFs built with hyperref carry link annotations from each `[12]` to its bib entry, so those fields can recover cite→bib links from a PDF without any NLP (technique, not yet tested — unverified). (2) GROBID remains the only PDF parser that resolves in-text markers to `<biblStruct>` entries itself, at F1 76.3 on PMC.

## (e) Math

**Extraction fidelity (LaTeX from PDF).** OmniDocBench formula CDM: PaddleOCR-VL-1.6 97.53 · MinerU2.5-Pro 97.45 · GLM-OCR 97.18 · Gemini 3 Pro 95.99 · dots.ocr 89.95 · Mistral OCR 89.91 · olmOCR 88.10 · Marker 85.24 · MinerU pipeline 83.07; Mathpix scored 86.6 on the 2024 v1.0 set and is absent from v1.6 ([OmniDocBench](https://raw.githubusercontent.com/opendatalab/OmniDocBench/main/README.md), [paper](https://arxiv.org/html/2412.07626v1)). On the arXiv-heavy olmOCR-bench "ArXiv" category: Chandra 2 86.9–90.2 · PaddleOCR-VL 85.7 · Marker 2 balanced 83.9 · olmOCR 2 83.0 · Mistral v1 77.2 · MinerU 2.5.4 76.6. Nougat's 2023 math F1 of 76.5 and non-commercial weights make it obsolete. Mathpix, the historical math specialist, now has no third-party 2026 number — treat its edge as unverified.

**Inline vs display in the parsers' outputs.** MinerU: `inline_equation` spans inside text blocks + `equation` blocks (LaTeX) — the cleanest fit for reflow. Mathpix: `\( \)` / `\[ \]` defaults, configurable, `include_equation_tags` keeps numbers. Marker: `TextInlineMath` vs `Equation` blocks, `<math>` tags in HTML. Mistral: `equation` block type for display; inline math is embedded in the markdown (delimiter convention not documented — unverified). Chandra: `equation-block` type; inline handling not documented. Docling: `FormulaItem` LaTeX via CodeFormula, HTML export through `latex2mathml`; inline-math detection inside paragraphs not documented (unverified). Azure DI: `kind: inline|display` with LaTeX, but formulas are `:formula:` placeholders placed "at the end of each page" — usable for detection, unusable for reflow position. GROBID: `<formula>` is raw text, no LaTeX.

**LaTeX → MathML for the reader.** Temml converts TeX math to MathML Core; supports `align/gather/cases/matrix`, macros, `\text{}` with nested math; does not support `\multicolumn`, `\cline`, `\par`; `throwOnError:false` renders errors in `errorColor` instead of failing; `annotate:true` keeps the TeX inside `<annotation>` (same shape as arXiv HTML); needs Temml.woff2 (~10 KB) for `\mathscr` and prime alignment in Chromium ([supported](https://temml.org/docs/en/supported.html), [administration](https://temml.org/docs/en/administration.html)). Practical rule: run every OCR'd LaTeX string through Temml at parse time; strings Temml rejects get stored as LaTeX text with the block flagged, so the offset model is never broken by a bad formula.

**How products handle math in reflow.** They mostly don't: Semantic Reader, alphaXiv, Paperpile, ReadCube, SciSpace, Zotero (PDF) and Sioyek all show the PDF's rendered math. Zotero's reflowed EPUB view renders MathJax from `data-tex` ([math.ts](https://github.com/zotero/reader/blob/master/src/dom/common/lib/math.ts)). arXiv HTML ships MathML with a TeX annotation, which is the model to copy: MathML for display and selection, TeX kept for copy/AI. Source of truth for arXiv ids stays the HTML.

## (f) Recommendation

Both paths emit one block model (`{id, type, level?, text, latex?, mathml?, caption?, refs?, prov[]}` in reading order); offsets and sentence ids are minted after parsing, once, per parser version.

**Local TypeScript path (Electron main): arXiv HTML → OpenAlex TEI → hosted OCR API.** Unchanged in shape; the OCR tier changes.

1. **Datalab Convert API, `mode=accurate`, `output_format=json`, `add_block_ids`, `merge_cross_page`, `extras=extract_links`.** Best hosted number on the arXiv-heavy benchmark (86.7; Chandra 2 85.8 with ArXiv 87–90 and multi-column 82–84), typed blocks including `equation-block`, `footnote`, `bibliography`, `page-header/footer`, section hierarchy, cross-page merging and link extraction built in ([convert API](https://documentation.datalab.to/api-reference/convert-document.md), [Chandra](https://github.com/datalab-to/chandra)). $10/1k pages ($4 for balanced = Marker 2, 76.0). Trade-off: vendor claims on a benchmark the vendor also argues is saturated; no offsets; no reading-order number on OmniDocBench for Chandra.
2. **Mistral OCR 4.1 (`mistral-ocr-4-1`, `include_blocks`, block confidence, `extract_header/footer=false`).** Cheapest structured hosted output ($4/1k, $2 batch), 13 block types that already isolate `equation`, `references`, `header`, `footer`, `hyperlinks` for cite links, GA and pinnable. Trade-off: the only third-party numbers are for older versions (72.0 olmOCR-bench v1; 85.66 OmniDocBench, read-order 0.171 — the weakest ordering among the finalists); the 85.2 for OCR 4 is self-reported. Keep as the price-tier default and A/B it against Datalab on the product's own 50-paper eval before choosing.

Runners-up, and why not: Mathpix ($5/1k) has the best-designed math output (`\( \)`/`\[ \]`, `section_header` line types, equation tags) but no 2026 third-party benchmark; Azure DI is the only API with document offsets and inline/display formula kinds, but formulas are detached to page end and it costs ~$10/1k plus an add-on; LlamaParse "agentic plus" is $56/1k for no published accuracy; Reducto has no formula type; Gemini/Claude return no structure.

**Cloud Python path (GPU): best open parser, self-hosted.**

1. **MinerU 3.4, hybrid backend (`effort=high`, MinerU2.5-Pro-2605-1.2B).** Best reading order on OmniDocBench (0.120), formula CDM 97.45, inline math as spans inside text, typed `content_list` with footnotes/references/headers/footers and paragraph-merge, 1.2B params (8 GB VRAM, 2.1 fps on one A100), Apache-2.0 weights. Trade-offs: the "MinerU Open Source License" requires prominently stating MinerU is used (a settings-page line satisfies it); olmOCR-bench score for the hybrid backend is unpublished (pipeline 72.7–75.2, arXiv 76.6 — weaker than Chandra on the English/arXiv set); trained on a Chinese-heavy mix, so run the internal eval before trusting it on arXiv typography.
2. **Chandra 2 (self-hosted via vLLM).** Highest open score on the arXiv-heavy benchmark (85.8; ArXiv 86.9–90.2, tables 89.9–92.1) with 18 block types. Trade-offs: OpenRAIL-M weights free only under $2M funding/revenue and "cannot be used competitively with our API" — acceptable now, a licensing cliff later; 4–5B params want an H100-class card (2 pg/s at 96 concurrent); no OmniDocBench reading-order number. If the product will earn money, budget the commercial license or prefer #1.
3. **Marker 2 balanced (self-hosted).** The pragmatic pipeline: 83.5 on born-digital PDFs (the arXiv case), JSON tree with `section_hierarchy`, `TextInlineMath`/`Equation`, `Footnote`, `Reference`, hyphenation and column/page merge in code you can read, 2.9 pg/s on a B200. Trade-offs: worst reading-order edit distance in the OmniDocBench table (0.243), formula CDM 85.2, weights limited to <$5M funding/revenue. Docling 2.126 is the license-clean alternative (MIT, item charspans, hyphenation and merges in source, MathML export) at 50.3/64.0 — right choice only if the OpenRAIL clauses are unacceptable. PaddleOCR-VL-1.6 (Apache-2.0, 0.9B, OmniDocBench 96.34) is the wildcard: its olmOCR-bench score is unverified and possibly poor, so it needs the internal eval before it displaces any of the three.

**What to keep from F2.** arXiv HTML first (source of truth, math already MathML+TeX); OpenAlex TEI for OA DOIs without heavy math (GROBID gives cite→bib links no OCR does, F1 76.3); hosted OCR for uploads and fallbacks. **What changes.** Mistral drops from default to price tier; Datalab accurate becomes the quality tier; a GPU box running MinerU hybrid (or Chandra 2 if the license fits) replaces "docling compose profile" as the self-host story, with Docling kept only as the MIT fallback. Because offsets are minted by us, swapping any of these later costs one re-parse and a Hypothesis-style re-anchor, which F3 already budgets for.
