# Explainer rendering: Manim-as-a-service and R3F-from-JSON (facts, 2026-09-05)

Scope: product-facing facts for "Explainers" — seconds-long, single-concept animations. Two media are on the table: Manim scenes rendered on a cloud service, and interactive 3D mechanisms rendered live in the Electron renderer by React Three Fiber (R3F) from a constrained JSON schema. This note does not choose a stack; it records what each medium can and cannot do, what latency to plan for, and what may legally ship. Every latency figure here is an **estimate** unless a URL says otherwise — none of the projects publish render-time numbers.

## (a) Manim as a service

**What one render does.** Manim Community (ManimCE) runs `Scene.setup() → construct() → tear_down()`; each `Animation` is interpolated 0→1 over its frames and the renderer pipes frames to FFmpeg ([deep dive](https://docs.manim.community/en/stable/guides/deep_dive.html)). `SceneFileWriter.write_frame` "is used internally by Manim to write a frame to the FFMPEG input buffer"; every animation becomes its own **partial movie file** named by a hash (`add_partial_movie_file` — "adds a new partial movie file path … from a hash"), and `combine_to_movie` "combines the separate partial movie files that make up a Scene into a single video file" ([SceneFileWriter](https://docs.manim.community/en/stable/reference/manim.scene.scene_file_writer.SceneFileWriter.html)). The deep dive adds: "Depending on the encoding configuration, the partial movie file can continue encoding while the next animation is rendered." Caching is per animation: `is_already_cached` "will check if a file named with hash_invocation exists"; `--disable_caching` turns lookup off "(still generates cache files)", `--flush_cache` removes them ([configuration](https://docs.manim.community/en/stable/guides/configuration.html)).

**Quality presets** (documented, [configuration](https://docs.manim.community/en/stable/guides/configuration.html)): `-ql` 854x480 @ 15 fps · `-qm` 1280x720 @ 30 fps · `-qh` 1920x1080 @ 60 fps · `-qp` 2560x1440 @ 60 · `-qk` 3840x2160 @ 60. Resolution and fps are independently settable (`-r/--resolution`, `--fps`), so "1080p at 30 fps" is `-r 1920,1080 --fps 30`, halving the frame count of `-qh` ([CLI render](https://docs.manim.community/en/stable/reference/manim.cli.render.html)). Frame budget for a 5–15 s scene: 75–225 frames at `-ql`, 150–450 at 1080p30, 300–900 at `-qh`.

**Output formats.** `--format png|gif|mp4|webm|mov`; `-g/--save_pngs` "save all frames in the scene as images files"; `-s/--save_last_frame` renders "only the last frame of a scene as a PNG image"; `-t/--transparent`; `--save_sections` writes one video per `self.next_section()` plus a JSON with codec, dimensions, frame rate, duration and frame count ([configuration](https://docs.manim.community/en/stable/guides/configuration.html), [output tutorial](https://docs.manim.community/en/stable/tutorials/output_and_config.html), [ManimConfig](https://docs.manim.community/en/stable/reference/manim._config.utils.ManimConfig.html)). `-n a,b` renders only animations a..b ([configuration](https://docs.manim.community/en/stable/guides/configuration.html)).

**Is progressive preview feasible?** Yes, with three documented hooks, none of which is a streaming API:
1. *Per-animation partial movie files* land on disk as each `play()` finishes (hash-named, under `media/videos/<scene>/<res>/partial_movie_files/`, [output tutorial](https://docs.manim.community/en/stable/tutorials/output_and_config.html)). A service can watch that directory and ship segments before `combine_to_movie` runs. This is the natural "first frames early" path.
2. *`--format=png` / `-g`* writes every frame as an image; frames can be tailed and streamed as they appear. Cost: PNG encode per frame and no inter-frame compression.
3. *`-s` last-frame PNG* is the documented "fastest preview option" and is the right first response for a still thumbnail ([output tutorial](https://docs.manim.community/en/stable/tutorials/output_and_config.html)).
Two things do not exist: a documented frame-streaming socket, and a low-latency live renderer for servers. ManimCE's OpenGL renderer does "a live preview in a popup window" and `Scene.interactive_embed` offers "interaction with Scene via mouse and keyboard as well as dynamic commands via an iPython terminal", but only with `--renderer=opengl`, a window, and not while `write_to_movie`/`format`/`dry_run` are set — it is a desktop authoring tool, not a headless preview path ([configuration](https://docs.manim.community/en/stable/guides/configuration.html), [scene source](https://docs.manim.community/en/stable/_modules/manim/scene/scene.html)). ManimCE's own OpenGL docs admit "the official online documentation does not contain the relevant base classes like `OpenGLMobject`" ([OpenGL FAQ](https://docs.manim.community/en/stable/faq/opengl.html)). The Electron-based `manim-renderer` that did stream to WebGL was archived 2021-06-15 ([manim-renderer](https://github.com/ManimCommunity/manim-renderer)). manimgl (3b1b's fork) is live-first — "A window will pop up on the screen", `self.embed()` opens an IPython terminal, `-w` writes, `-o` writes and opens, `-s` skips to the last frame ([manimgl quickstart](https://3b1b.github.io/manim/getting_started/quickstart.html), [3b1b/manim README](https://raw.githubusercontent.com/3b1b/manim/master/README.md)) — but it is the same desktop-window model.

**Hosted renderers and notebooks.** ManimCE ships a `%%manim` Jupyter magic, runs on Binder at try.manim.community (repo [jupyter_examples](https://github.com/ManimCommunity/jupyter_examples)) and on Google Colab after apt/pip install; the docs make no latency or resource claims for either ([Jupyter install](https://docs.manim.community/en/stable/installation/jupyter.html)). The official Docker image `manimcommunity/manim` "ships with a minimal TeX Live installation" and disallows `-p`/`-f`; image size is not documented ([Docker install](https://docs.manim.community/en/stable/installation/docker.html)). Third-party hosted "Manim render API" spaces exist on Hugging Face (e.g. MathFrames/manim-render-api) but publish no render-time, hardware or limit claims — their READMEs are SDK metadata only ([HF space](https://huggingface.co/spaces/MathFrames/manim-render-api/blob/main/README.md)). Conclusion: no hosted Manim renderer publishes a latency number; there is nothing first-party to cite.

**Latency to plan for (all estimates, single CPU worker, Cairo renderer, no GPU needed).** Manim is CPU-bound Cairo rasterisation plus FFmpeg; text with `Tex`/`MathTex` adds a LaTeX+dvisvgm compile per distinct string on first use (cached afterwards).
- Cold start of a container with TeX Live + Manim: ~5–30 s depending on image pull/warmth *(estimate)*. Keep a warm pool; this dominates the "first explainer" experience otherwise.
- `-s` last-frame PNG: ~1–5 s *(estimate)*; the first artifact worth showing.
- `-ql` (480p15) 5–15 s scene: ~5–20 s render+encode *(estimate)*; `-n` and per-animation cache make re-renders of an edited scene cheaper.
- 1080p30 (`-r 1920,1080 --fps 30`) 5–15 s scene: ~20–90 s *(estimate)*; `-qh` at 60 fps roughly doubles.
- Transfer: a 10 s 1080p H.264 clip is single-digit MB; negligible against render.
- Time-to-first-segment with the partial-movie-file watch: roughly the first `play()`'s share of the total, i.e. seconds, not the full render *(estimate)*.
Nothing here is real time. A Manim explainer is a *generated video asset*: request → wait tens of seconds → play/scrub a file.

## (c) React Three Fiber from a constrained JSON schema

**Why a JSON schema maps cleanly onto R3F.** R3F "is a React renderer for three.js"; "Everything that works in Threejs will work here without exception" and "There is no overhead" ([introduction](https://r3f.docs.pmnd.rs/getting-started/introduction)). JSX names are camelCased three.js classes; "Constructor arguments are always passed as an array via `args`"; properties with `.set()` accept arrays/strings (`color="hotpink"`, `scale={1}`); nested props use dash-case (`rotation-x`, `material-color`); `extend({ CustomClass })` registers new classes; `<primitive object={…} />` mounts an existing object ([objects](https://r3f.docs.pmnd.rs/api/objects)). So a schema node `{type:"mesh", geometry:{type:"boxGeometry", args:[1,1,1]}, material:{type:"meshStandardMaterial", color:"#c8a"}, position:[0,1,0]}` is a one-to-one transcription into JSX — the "loader" is a ~50-line recursive component, and any three.js class the schema whitelists is available for free.

**What the schema can realistically express live (all first-party-supported):**
- *Primitives and materials*: every `*Geometry` and `*Material` class by name + `args` ([objects](https://r3f.docs.pmnd.rs/api/objects)); shader-based `Grid` with `cellSize`, `sectionSize`, `fadeDistance`, `infiniteGrid` ([drei Grid](https://drei.docs.pmnd.rs/gizmos/grid)); CatmullRom splines "A curve representing a Catmull-Rom spline" with `centripetal|chordal|catmullrom`, `closed`, `tension`, `getPoint(t)` ([CatmullRomCurve3](https://raw.githubusercontent.com/mrdoob/three.js/dev/src/extras/curves/CatmullRomCurve3.js)).
- *Transforms*: `position/rotation/scale` arrays, or a full 4x4 `matrix` as in three's own JSON.
- *Keyframed animation*: three's `AnimationClip {name, duration, tracks}` with `Number/Vector/Quaternion/Color/Boolean/String KeyframeTrack`, `InterpolateLinear|Smooth|Discrete`, `toJSON()/parse()`; `AnimationMixer.setTime(t)`, `action.time`, `action.paused`, `setEffectiveTimeScale` ([AnimationClip](https://threejs.org/docs/#api/en/animation/AnimationClip)). drei `useAnimations` "abstracts AnimationMixer" and exposes `mixer, actions, names, clips` ([useAnimations](https://drei.docs.pmnd.rs/abstractions/use-animations)). This is the scrubbable, serialisable form.
- *Spring animation*: react-spring is "a cross-platform spring-physics first animation library" with a react-three-fiber target (`animated.mesh` etc.) ([README](https://raw.githubusercontent.com/pmndrs/react-spring/main/README.md)). Springs are for *interaction feel* (a gear settling), not for scrubbing — they have no timeline.
- *Scrub/timeline control*: R3F `frameloop="demand"` renders only when `invalidate()` is called; `frameloop="never"` renders only on `advance(timestamp)` ([hooks](https://r3f.docs.pmnd.rs/api/hooks), [scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance)). A slider bound to `mixer.setTime(t)` + `invalidate()` gives deterministic scrubbing at zero idle GPU cost. Remotion's `<ThreeCanvas>` uses exactly this: "During rendering, `<ThreeCanvas>` overrides the `frameloop` prop to `'never'`… it is only re-rendered on demand via `advance()`", and animations are written against `useCurrentFrame()` rather than `useFrame` ([ThreeCanvas](https://www.remotion.dev/docs/three-canvas), [@remotion/three](https://www.remotion.dev/docs/three)). Scroll-driven timelines: drei `ScrollControls` (`pages`, `damping`, `useScroll().offset/range/curve`; "DOM only") ([ScrollControls](https://drei.docs.pmnd.rs/controls/scroll-controls)).
- *Per-frame procedural motion*: `useFrame((state, delta) => …)` with `renderPriority`; the docs' hard rule is "You should never setState in there!" — mutate refs ([hooks](https://r3f.docs.pmnd.rs/api/hooks)). A schema can carry a small whitelist of expressions (`rotation.z = t * ratio`) rather than arbitrary code.
- *Labels*: drei `Html` "Allows you to tie HTML content to any object of your scene. It will be projected to the objects whereabouts automatically" with `occlude`, `transform`, `distanceFactor`, `center` — caveats: blending-occlusion only for rectangles, `transform` mode "may appear blurry" on some devices ([drei Html](https://drei.docs.pmnd.rs/misc/html)). Because it is real DOM, MathML/KaTeX labels work in it; this is how math typesetting reaches the 3D scene. In-scene text: drei `Text` = "Hi-quality text rendering w/ signed distance fields (SDF) and antialiasing, using troika-3d-text", suspends while the font loads ([drei Text](https://drei.docs.pmnd.rs/abstractions/text)) — glyphs only, no math layout. Three's own `CSS2DRenderer`: "The only transformations that are supported are translation and 2D rotation" ([CSS2DRenderer](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/jsm/renderers/CSS2DRenderer.js)).
- *Camera*: `OrbitControls`/`CameraControls`/`TrackballControls`/… with damping on by default and compatible with `frameloop="demand"` ([drei controls](https://drei.docs.pmnd.rs/controls/introduction)); camera paths = a `CatmullRomCurve3` sampled by `getPoint(t)` inside the same timeline.
- *Interaction*: pointer events on any mesh are native to R3F (`onPointerDown`, `onPointerMove` on `<mesh>`); a schema needs only to name which node is draggable and which parameter it drives.

**Existing schema-to-scene systems (first-party docs).**
- *Three.js JSON Object/Scene format 4* — `ObjectLoader` is "A loader for loading a JSON resource in the JSON Object/Scene format"; it parses shapes, skeletons, geometries, materials, animations (via `AnimationClip.parse`), images, textures and objects; objects carry `matrix`, `layers`, `userData` ([ObjectLoader source](https://raw.githubusercontent.com/mrdoob/three.js/dev/src/loaders/ObjectLoader.js), [format wiki](https://github.com/mrdoob/three.js/wiki/JSON-Object-Scene-format-4)). It is a complete, first-party, serialisable scene+animation format; its weakness for us is verbosity (explicit buffer geometry, UUID cross-refs, 4x4 matrices) and no notion of interaction or labels. Good as an *interchange* target, poor as an LLM-authored source.
- *Theatre.js* — keyframes with cubic-Bezier "speed curves", `sequence.play()/pause()/position` for scrubbing, `attachAudio`, prop types `number, rgba, boolean, string, stringLiteral, compound, image`; state is a JSON exported from the studio and loaded with `getProject(name, { state })`; `@theatre/r3f` gives `editable.mesh`, `editable.group`, editable cameras via `SheetProvider` ([sequences](https://www.theatrejs.com/docs/latest/manual/sequences), [projects](https://www.theatrejs.com/docs/latest/manual/projects), [prop types](https://www.theatrejs.com/docs/latest/manual/prop-types), [r3f](https://www.theatrejs.com/docs/latest/api/r3f)). It is the closest thing to "JSON timeline for R3F", but the studio is AGPL (see (b)) and the state format is the editor's, not a documented authoring schema.
- *Remotion* — frame-deterministic React; `renderFrames` "Renders a series of images using Puppeteer", concurrency "half of the CPU threads available", `renderMedia` stitches with FFmpeg; Three.js needs `--gl=angle` ("Three.JS does not render with the default OpenGL renderer") ([renderFrames](https://www.remotion.dev/docs/renderer/render-frames), [gl options](https://www.remotion.dev/docs/gl-options), [@remotion/three](https://www.remotion.dev/docs/three)). Relevant as proof that an R3F scene driven by a frame index can also be exported to video — same scene, two media.
- *Motion Canvas* — "A TypeScript library that uses generators to program animations" plus "an editor providing a real-time preview"; 2D canvas, no 3D ([README](https://raw.githubusercontent.com/motion-canvas/motion-canvas/main/README.md)). A code-first Manim alternative that runs in the browser, not a schema.
- *Manim scene JSON* — none exists. Manim scenes are Python; the only JSON Manim emits is the `--save_sections` metadata (codec, dimensions, fps, duration, frame count) ([output tutorial](https://docs.manim.community/en/stable/tutorials/output_and_config.html)).

## (d) What the two reference genres need from the schema

**3Blue1Brown-style transformation (linear map on a grid).** Needs: a grid (drei `Grid` or a `Line` set), a set of basis vectors/points as instanced meshes, one *matrix-valued parameter* interpolated 0→1 (identity → target), labels that track points (`Html` with math), and a timeline that can pause at t=0.5. In schema terms: `parameters: [{name:"t", range:[0,1]}]`, node transforms allowed to reference `lerp(I, M, t)`, and a `timeline` of keyframes on `t`. Everything is expressible with three's `VectorKeyframeTrack` on positions or a single `NumberKeyframeTrack` on `t` plus a per-frame mutation in `useFrame`. Grant's own tooling for this is Python (`LinearTransformationScene` in manimgl); reproducing his *scene code* is barred by CC BY-NC-SA (see (b)); reproducing the idea is not.

**Ciechanowski-style mechanism (a gear train you can turn).** Needs: parametric solids (gear = extruded profile; `extrudeGeometry` from a `Shape` is a three primitive), a *kinematic constraint* expressed as ratios (`gearB.rotation.z = -gearA.rotation.z * (teethA/teethB)`), a draggable handle mapped to one scalar, damping/inertia when released (react-spring), orbit camera, and exploded/section views as a second scalar. The essential schema feature is **one or two exposed scalars that drive derived transforms**, not keyframes. Ciechanowski's essays are hand-written WebGL per article; there is no schema to borrow, but the interaction grammar (scrub slider, drag on object, orbit) is exactly what `frameloop="demand"` + pointer events + `OrbitControls` provide.

**Constraint the schema must impose.** No arbitrary code: a closed set of node types, a closed set of expression functions (`lerp, sin, cos, clamp, ratio`), keyframe tracks in three's own JSON shape, and a `labels[]` list rendered through `Html`. That keeps LLM output validatable and keeps the renderer a pure function of JSON.

## (e) Latency and interactivity table

| Medium | Latency to first frame | Interactivity | Good for | Cannot do |
|---|---|---|---|---|
| Manim (cloud, Cairo), thumbnail via `-s` | ~1–5 s warm, +5–30 s cold *(estimate)* | none (still) | Instant placeholder while the clip renders | motion |
| Manim (cloud), `-ql` 480p15 preview, partial-movie-file streaming | first segment in seconds, full 5–15 s clip in ~5–20 s warm *(estimate)* | play/pause/seek a video; **no** scrub of scene parameters, no rotate | Fast iteration on a generated scene; low-stakes inline previews | change anything without a re-render; 3D camera control |
| Manim (cloud), 1080p30 final | ~20–90 s warm (+cold start) *(estimate)*; `-qh` 60 fps ~2x | video seek only | Polished 2D math typography (LaTeX native), 3b1b-grade morphs, exact vector text | any user parameter; live labels; hover |
| R3F live from JSON schema (`frameloop="demand"`) | one frame after JSON arrives: tens of ms to first paint after geometry build *(estimate; GPU-bound, no documented number)* | scrub timeline (`mixer.setTime`), rotate (`OrbitControls`), drag/parameter change (pointer events + spring), hover labels (`Html`) | Mechanisms, 3D transformations, anything the user should *touch*; Ciechanowski-style pieces | LaTeX-grade in-scene typography (only via DOM `Html`), cinematic 2D morphing of glyph outlines, Manim's vector text effects |
| R3F scene exported to video (Remotion `ThreeCanvas`, `--gl=angle`) | Puppeteer per-frame screenshots at half-CPU concurrency, then FFmpeg *(estimate: tens of seconds for 10 s clip)* | video seek | Same JSON, shareable MP4 | interactivity; requires headless Chrome infra and Remotion license terms |

Bottom line for the product: Manim is the *asset* medium (wait, then watch); R3F-from-schema is the *instrument* medium (touch immediately). They are complementary, and a schema built on three's own `AnimationClip` JSON keeps the R3F path exportable to video later.
